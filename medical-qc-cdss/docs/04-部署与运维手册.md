# 部署与运维手册

## 1. 部署形态

| 形态 | 组件 | 适用 |
| --- | --- | --- |
| 最小演示 | api + redis | 开发、演示、CI |
| 单机生产 | api×2 + redis + mysql + nginx | 单院区，日质控 < 1000 份 |
| 标准私有化 | 上述 + Milvus（etcd/minio）+ vLLM | 三甲医院 |
| K8s | Deployment + HPA + GPU Operator + Milvus Operator | 多院区、统一运维 |

## 2. 前置条件

| 项 | 要求 |
| --- | --- |
| OS | Linux（CentOS 7+/Ubuntu 20.04+）；开发可用 Windows/macOS |
| Docker | ≥ 24，Compose v2.24+（使用 `env_file.required`） |
| GPU（私有化） | NVIDIA A100/A800 80G ×1（32B-AWQ）或 2×4090（24G，需 TP=2 + 更小上下文） |
| 驱动 | ≥ 535，nvidia-container-toolkit 已安装 |
| 网络 | 院内可访问 EMR/His；除云模式外无需公网 |
| 磁盘 | 模型缓存 ≥ 100G；数据库按 3 年数据估算；日志 ≥ 50G |

## 3. Compose 部署

### 3.1 启动组合

```bash
cp .env.example .env

# 最小：mock 模型
docker compose up -d --build api redis

# 标准私有化
docker compose --profile mysql --profile milvus --profile gateway up -d --build

# 加 vLLM（GPU）
docker compose --profile gpu up -d vllm
```

| Profile | 服务 |
| --- | --- |
| 默认 | api、redis |
| `mysql` | mysql |
| `milvus` | etcd、minio、milvus |
| `gpu` | vllm |
| `gateway` | nginx |

### 3.2 数据目录权限（Linux 必读）

容器内以非 root 用户 `qc`（UID 10001）运行，bind mount 的 `./data` 需可写：

```bash
mkdir -p data reports
sudo chown -R 10001:10001 data reports
```

否则 SQLite 初始化会报 `unable to open database file`，且质控结果无法落库。
Windows Docker Desktop 的 bind mount 通常不受此限制。

### 3.3 关键环境变量

| 变量 | 说明 | 生产建议 |
| --- | --- | --- |
| `QC_LLM_PROVIDER` | `vllm` / `cloud` / `mock` | `vllm` |
| `QC_LLM_BASE_URL` | 推理服务地址 | `http://vllm:8000/v1` |
| `QC_LLM_MODEL` | 模型名（需与 vLLM `--served-model-name` 一致） | `Qwen2.5-32B-Instruct-AWQ` |
| `QC_LLM_JSON_MODE` | `guided` / `json_object` / `prompt_only` | `guided` |
| `QC_LLM_FALLBACK_PROVIDER` | 主模型故障降级 | `cloud` 或 `none`（按合规） |
| `QC_VECTOR_STORE` | `milvus` / `chroma` / `memory` | `milvus` |
| `QC_EMBEDDING_PROVIDER` | `openai` / `hash` | `openai`（BGE-M3） |
| `QC_DATABASE_URL` | 数据库连接 | `mysql+asyncmy://...` |
| `QC_REDIS_URL` | 缓存 | `redis://redis:6379/0` |
| `QC_AUTH_ENABLED` | 是否开启 JWT | `true` |
| `QC_PII_MASKING` | 等长脱敏 | `true` |
| `QC_MAX_CONCURRENCY` | 全局并发 | 按显存与压测定 |
| `QC_REQUEST_DEADLINE_S` | 请求截止 | 45 |

```bash
python scripts/smoke.py --base-url http://localhost:8000
```

## 4. vLLM 部署与调优

### 4.1 启动参数

```bash
vllm serve Qwen/Qwen2.5-32B-Instruct-AWQ \
  --served-model-name Qwen2.5-32B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --max-num-seqs 64 \
  --disable-log-requests
```

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `--max-model-len` | 上下文上限 | 8192；病历分片后足够 |
| `--gpu-memory-utilization` | 显存占用上限 | 0.85–0.92 |
| `--enable-prefix-caching` | 复用系统提示词 KV | 必开，TTFT 明显下降 |
| `--enable-chunked-prefill` | 长 prompt 分块 | 长病历场景必开 |
| `--max-num-seqs` | 并发序列 | 与显存匹配，过大反而排队 |
| `--tensor-parallel-size` | 多卡切分 | 24G 卡跑 32B 需 TP=2 |
| `--guided-decoding-backend` | 受约束解码后端 | 默认 xgrammar |

### 4.2 显存估算

| 模型 | 量化 | 权重 | KV/Token | 80G 卡可承载（2k 上下文） |
| --- | --- | --- | --- | --- |
| 32B | AWQ 4bit | ≈19 GB | ≈256 KiB | ≈100 并发（理论） |
| 32B | FP16 | ≈64 GB | ≈256 KiB | ≈30 并发 |
| 14B | AWQ | ≈9 GB | ≈128 KiB | ≈200 并发 |
| 7B | AWQ | ≈5 GB | ≈64 KiB | ≈400 并发 |

> 生产以压测为准，按 P95 时延与显存水位反推 `max-num-seqs` 与 `QC_MAX_CONCURRENCY`。

### 4.3 Embedding 服务

BGE-M3 可用单独进程（推荐，避免与生成模型抢显存）：

```bash
vllm serve BAAI/bge-m3 --task embed --port 8002
# .env
QC_EMBEDDING_PROVIDER=openai
QC_EMBEDDING_BASE_URL=http://vllm-embed:8000/v1
QC_EMBEDDING_MODEL=bge-m3
QC_EMBEDDING_DIM=1024
```

维度必须与 Milvus collection 一致；变更维度需重建 collection。

## 6. K8s 参考

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: qc-cdss-api
spec:
  replicas: 2
  selector:
    matchLabels: { app: qc-cdss-api }
  template:
    metadata:
      labels: { app: qc-cdss-api }
    spec:
      containers:
        - name: api
          image: registry.local/qc-cdss:0.1.0
          ports: [{ containerPort: 8000 }]
          envFrom:
            - secretRef: { name: qc-cdss-secrets }
            - configMapRef: { name: qc-cdss-config }
          readinessProbe:
            httpGet: { path: /readyz, port: 8000 }
            initialDelaySeconds: 20
            periodSeconds: 10
          livenessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 30
            periodSeconds: 20
          resources:
            requests: { cpu: "1", memory: 2Gi }
            limits: { cpu: "4", memory: 4Gi }
```

要点：

- api 无状态，可水平扩展；**并发上限由 GPU 决定**，副本数增加不必然提升吞吐；
- 每个 api 副本都会启动时加载知识库到内存，需关注内存；
- vLLM 用独立 Deployment + GPU 节点亲和，`hostIPC: true`，`NVIDIA_VISIBLE_DEVICES`；
- 用 HPA 基于 CPU/QPS 扩容 api，但需配合网关限流，避免打爆推理服务。

## 7. 监控与告警

### 7.1 指标

| 指标 | 类型 | 告警建议 |
| --- | --- | --- |
| `qc_requests_total{status}` | Counter | 错误率 > 2% 持续 5min |
| `qc_request_latency_seconds` | Histogram | P95 > 10s 持续 10min |
| `llm_ttft_seconds` | Histogram | P95 > 3s |
| `llm_calls_total{status="error"}` | Counter | 5min 内 > 1% |
| `qc_degraded_total` | Counter | 降级率 > 5% |
| `evidence_verification_total{state="invalid"}` | Counter | invalid 占比 > 15% 需排查提示词 |
| `cache_events_total` | Counter | 命中率 < 30% 检查 key |
| GPU 显存/利用率 | node-exporter/DCGM | 显存 > 95% 或 OOM |
| `/readyz` | 探针 | 连续失败 3 次 |

### 7.2 告警规则示例

```yaml
groups:
  - name: qc-cdss
    rules:
      - alert: QcHighErrorRate
        expr: sum(rate(qc_requests_total{status="failed"}[5m])) / sum(rate(qc_requests_total[5m])) > 0.02
        for: 5m
        labels: { severity: P1 }
        annotations:
          summary: "质控失败率超过 2%"

      - alert: QcLatencyHigh
        expr: histogram_quantile(0.95, sum(rate(qc_request_latency_seconds_bucket[5m])) by (le)) > 10
        for: 10m
        labels: { severity: P2 }

      - alert: LlmFallbackActive
        expr: increase(qc_degraded_total{reason=~"model.*"}[10m]) > 0
        for: 5m
        labels: { severity: P2 }
```

### 7.3 日志

- JSON 格式，字段：`ts/level/logger/trace_id/message/extra`；
- 不记录完整病历与 PII；引文最多 200 字且已脱敏；
- 采集：Filebeat/Fluent Bit → ES/Loki；保留 30 天；
- 按 `trace_id` 串联 HTTP → pipeline → LLM 调用。

## 8. 备份与恢复

| 对象 | 方式 | 频率 | 恢复 |
| --- | --- | --- | --- |
| MySQL | mysqldump + binlog | 每日 | 全量 + binlog 回放 |
| SQLite | `VACUUM INTO` 快照 | 每日 | 替换文件 |
| Milvus | 快照 / 源文档重建 | 每周 | `build_index.py` |
| 审计日志 | 对象存储（版本化） | 实时 | 只读挂载 |
| 配置文件 | Git 管理 `.env` 模板 | 变更时 | 检出 |

恢复演练每季度一次，记录 RTO。

## 9. 升级与回滚

```bash
# 1) 备份
mysqldump ... > backup_$(date +%F).sql

# 2) 拉取新镜像
docker compose pull api

# 3) 迁移（如涉及）
docker compose run --rm api alembic upgrade head

# 4) 滚动重启
docker compose up -d --no-deps api

# 5) 验证
curl -s localhost:8000/readyz
python scripts/smoke.py

# 回滚
docker compose up -d --no-deps api@sha256:<old>
```

灰度：nginx `split_clients` 按 header/uid 分流 10%，观察 30 分钟后放量。

## 10. 排障

| 现象 | 排查 | 处理 |
| --- | --- | --- |
| `/readyz` 503 | 看启动日志 `startup_complete` | 数据库/Redis/Milvus 连接；`startup_errors` |
| 首个请求超时 | vLLM 是否加载完模型 | 等待 `/health`；检查 GPU |
| SSE 不流式 | Nginx 缓冲 | `proxy_buffering off`；`X-Accel-Buffering: no` |
| 大量 structured retry | 模型不支持 json_schema | 切 `QC_LLM_JSON_MODE=json_object` |
| 证据 invalid 比例高 | 提示词被改 / 脱敏错位 | 回滚提示词；检查 `mask_pii_aligned` 长度 |
| Milvus 连接失败 | etcd/minio 未就绪 | `docker compose logs milvus` |
| 显存 OOM | 并发过大 / 上下文过长 | 降 `max-num-seqs`、`max-model-len` |
| 中文乱码 | 连接字符集 | URL 加 `charset=utf8mb4` |
| 时区差 8 小时 | 容器 TZ | 设置 `TZ=Asia/Shanghai` |

## 11. 安全加固清单

- [ ] 修改默认 `QC_JWT_SECRET`，开启 `QC_AUTH_ENABLED`
