## 阶段 01 · 服务骨架 ✅

### 1. 这一步做了什么

跑起来一个最小可用的 FastAPI 服务，它具备：

| 能力 | 落在哪 | 为什么现在就要 |
| --- | --- | --- |
| 统一入口 | `app/main.py` 的 `create_app()` | 后面所有模块都挂在这个 app 上 |
| 配置外置 | `app/core/config.py` | 换院、换模型、换端口不改代码 |
| 日志 | `app/core/logging.py` | 出问题第一件事是看日志 |
| 存活/就绪探针 | `app/api/health.py` | 部署、Nginx 摘流、容器健康检查都靠它 |
| 自动化验收 | `tests/test_health.py` | 没有测试的「能跑」都是暂时的 |

### 2. 三个必须理解的概念

**① 为什么探针要分 `/healthz` 和 `/readyz`**
- `/healthz` 只证明「进程活着」。它连 Redis 都不查——下游挂了不该重启本进程。
- `/readyz` 证明「能接业务」。依赖没就绪时返回 503，让网关摘流量，而不是给用户报错。
- 混成一个的后果：Redis 抖一下，容器被反复重启，故障被放大。

**② 为什么配置用环境变量 + pydantic-settings**
- 代码里出现 `10.x.x.30:8001` 这种地址，换院就要改代码、重新构建镜像。
- 用 `CDSS_` 前缀是防止和系统里的 `PORT`、`HOST` 撞车。
- 类型校验在**启动时**发生：端口写成 `abc` 直接起不来，而不是跑一半崩。

**③ 为什么要应用工厂 `create_app()`**
- 测试可以造一个「不读 .env 的干净 app」，结果才可复现。
- 将来多 worker、多租户、多套配置都靠它。
- 而 `app = create_app()` 这一行，保证 `uvicorn app.main:app` 依然能用。

### 3. 自己跑一遍（必须动手）

```powershell
# 启动
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

# 另开一个终端
curl http://127.0.0.1:8000/healthz
curl http://127.0.0.1:8000/readyz

# 跑测试
.\.venv\Scripts\python.exe -m pytest -v
```

预期：浏览器打开 http://127.0.0.1:8000/docs 能看到 3 个接口（`/`、`/healthz`、`/readyz`）。

### 4. 动手改一改（检验是否真懂）

1. 把 `.env.example` 复制成 `.env`，加一行 `CDSS_LOG_LEVEL=DEBUG`，重启后看日志级别有没有变。
2. 加一行 `CDSS_PORT=abc`，观察启动时报什么错——这就是「启动期校验」。
3. 把 `healthz` 的返回里加一个 `"hospital_id": "H001"` 字段，再跑测试确认没崩。
